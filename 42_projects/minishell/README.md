## 과제 개요

```bash
./minishell
```

bash의 핵심 동작을 구현한 인터랙티브 셸입니다.

**구현 범위**

| 기능 | 설명 |
|---|---|
| 프롬프트 | readline 기반 입력 |
| 파이프 | `\|` 으로 명령어 연결 |
| 리디렉션 | `<` `>` `>>` `<<` (히어독) |
| 환경 변수 | `$VAR` 확장, `$?` 종료 코드 |
| 쿼터 | `'단일 쿼터'`, `"더블 쿼터"` |
| 내장 명령어 | `echo`, `cd`, `pwd`, `export`, `unset`, `env`, `exit` |
| 시그널 | `Ctrl+C`, `Ctrl+D`, `Ctrl+\` |

## 전체 파이프라인

```
사용자 입력
    │
    ▼
토크나이징 (tokenize.c)
    └── 문자열 → 토큰 리스트 (이중 연결 리스트)
    │
    ▼
유효성 검사 (syntax_chk.c)
    └── syntax error 감지 → exit_code 258 부여
    │
    ▼
구문 분석 트리 생성 (tree_build.c)
    └── 토큰 리스트 → 트리 구조화
    │
    ▼
실행 (exec/)
    └── 트리 순회하며 명령 실행
        ├── 내장 명령어: 직접 실행
        └── 외부 명령어: fork + execve
```

**execve로 내장 명령어를 실행할 수 없는 이유**  
`cd`, `pwd`, `export` 같은 내장 명령어는 현재 셸 프로세스의 상태(현재 디렉토리, 환경 변수 등)를 변경해야 합니다.  
`execve`는 새로운 프로세스를 생성해 실행하므로, 현재 셸 프로세스에 영향을 줄 수 없습니다.  
내장 명령어는 반드시 현재 프로세스에서 직접 실행해야 하는 이유가 여기에 있습니다.  
구문 분석 트리를 왜 구현해야 하는지 이 사실을 알고 나서 바로 이해됐습니다.

## 토크나이징

입력 문자열을 개별 토큰으로 분리합니다. 컴파일러도 동일한 방법으로 소스 코드를 해석합니다.

**토큰 분리 규칙**

1. **공백** — 기본 구분자. 탭도 구분자로 처리.
2. **쿼터** — `'` 혹은 `"`가 나오면 닫히는 쿼터까지 단일 토큰. 쿼터 기호 자체는 토큰에 포함하지 않음.
3. **특수 문자** — `|`, `>`, `<`, `>>`, `<<` 는 공백 없이도 토큰으로 분리.
4. **환경 변수** — `$`로 시작하는 형식의 문자열은 별도 토큰으로 처리하지 않고, 길이 정보만 기록해둔 뒤 실행 직전에 확장.

**토큰 노드 구성요소**

```c
typedef struct s_token {
    char        *str;         // 토큰 문자열
    int         idx;          // 리스트 내 인덱스
    int         ctrl_token;   // 컨트롤 토큰 여부 (파이프, 리디렉션)
    int         quote_flag;   // 쿼터가 공백으로 바뀐 경우 플래그
    t_env_node  *env_lset;    // 환경 변수 이름 길이 배열
    struct s_token *prev;
    struct s_token *next;
} t_token;
```

`env_lset`을 배열로 준 이유: 하나의 토큰 안에 환경 변수가 여러 개 있을 수 있어 각각의 이름 길이와 더블쿼터 안에 있는지 여부를 기록해야 하기 때문입니다.

## 구문 분석 트리

토큰 리스트를 트리 구조로 변환해 명령어 간 관계를 표현합니다.

**트리 노드 구성요소**

```c
typedef struct s_tree {
    t_token         *tk_list;     // 토큰 리스트 시작 포인터
    int             node_idx;     // 노드 인덱스
    int             visited;      // 방문 여부
    int             ctrl_token;   // 파이프/리디렉션 종류
    int             ambiguous;    // ambiguous redirect 오류 플래그
    int             end_flag;     // 명령문 끝 노드 여부
    int             *token_idxs;  // 이 노드가 사용할 토큰 인덱스 배열
    int             exit_code;    // 오류 발생 시 종료 코드
    struct s_tree   *left;
    struct s_tree   *right;
    struct s_tree   *parent;
} t_tree;
```

**트리 구조 설계**

파이프를 기준으로 명령어 파트를 나눕니다.  
파이프 노드가 부모, 파이프 앞 파트가 왼쪽 자식, 뒤 파트가 오른쪽 자식이 됩니다.  
다중 파이프는 오른쪽 자식을 다음 파이프 노드로 연결해 재귀적으로 동일한 구조를 만듭니다.

```
ls -a >> a < b -l > c | grep "" | cat << x > y

          [pipe1]
         /       \
   [ls 서브트리]  [pipe2]
                 /       \
           [grep 서브트리]  [cat 서브트리]
```

**전위 순회 (Pre-order Traversal)**  
트리 실행 시 현재 노드 → 왼쪽 자식 → 오른쪽 자식 순서로 방문합니다.  
오른쪽 자식까지 방문이 끝나면 `end_flag`를 세워 실행부에 명령문 종료를 알립니다.

**토큰 인덱스 배열**  
노드에 토큰 문자열을 직접 복사하지 않고 토큰 리스트의 인덱스 번호만 담았습니다.  
인덱스로 토큰 리스트를 참조하면 문자열 외에 메타 정보(쿼터 여부, 환경 변수 정보 등)도 함께 가져올 수 있어 메모리 낭비 없이 효율적입니다.

## 리디렉션 파싱

### 리디렉션 기호 위치는 결과에 영향 없음

셸은 명령줄 전체를 먼저 읽고 흐름 구조를 파악하기 때문에, 리디렉션 기호 위치가 달라도 결과가 같습니다.

```bash
echo hoho > test.txt
> test.txt echo hoho   # 동일한 결과
```

```bash
cat < test.txt > test2.txt
< test.txt > test2.txt cat   # 동일한 결과
```

리디렉션 기호 바로 뒤 토큰은 무조건 파일명이며, 명령어나 옵션은 될 수 없습니다.

### 리디렉션 오버로딩

같은 방향의 리디렉션이 여러 개 있으면 마지막 것만 유효합니다.  
단, 앞의 리디렉션들도 구문 분석 트리에 포함시키고 실행 파트에서 처리합니다. (실제 bash 동작과 동일)

### 서브트리 조합 (reassembly)

파이프로 나뉜 각 명령어 파트를 서브트리로 조합할 때 두 단계로 처리합니다.

1. **왼쪽 리디렉션 파트** — `<`, `<<` 기호들을 왼쪽 자식 노드로 배치. 통로 명령어도 이 단계에서 조합.
2. **오른쪽 리디렉션 파트** — `>`, `>>` 기호들을 오른쪽 자식 노드로 배치.

명령어 조합 방법: 리디렉션 기호 바로 뒤 토큰(파일명)을 제외한 나머지 토큰을 왼쪽부터 순서대로 명령어로 조합합니다.

## 환경 변수 확장

### 확장 시점을 실행 직전으로 미룬 이유

토크나이징이나 파싱 단계에서 환경 변수를 확장하면, 실행 도중 `export`로 새로 추가된 환경 변수는 확장할 수 없습니다.  
따라서 환경 변수 확장은 각 명령 실행 직전에 수행합니다.

대신 **토크나이징 단계에서 환경 변수처럼 보이는 이름의 길이만 미리 기록**해두고 (`env_lset`),  
실행 단계에서 이 길이 정보를 참고해 실제 환경 변수 목록과 대조해 확장합니다.

### 쿼터별 확장 규칙

- **싱글 쿼터** 안: 환경 변수 확장 없음. `env_lset` 길이를 0으로 기록해 확장 단계에서 건너뜀.
- **더블 쿼터** 안: 환경 변수 확장 수행.
- **쿼터 없음**: 환경 변수 확장 수행. 확장 결과에 공백이 포함되면 별도 처리.

쿼터가 먼저 나온 쪽이 해당 문자열을 "장악"합니다.  
예: `" ' ' "` → 더블 쿼터 장악, 싱글 쿼터는 일반 문자 처리.  
예: `' " " '` → 싱글 쿼터 장악, 더블 쿼터는 일반 문자 처리.

### ambiguous redirect 오류

리디렉션 파일명에 환경 변수를 사용할 때 발생하는 오류입니다.

- 환경 변수 확장 결과가 빈 문자열이거나 공백이 포함된 경우 → `ambiguous redirect` 오류
- 단, 더블 쿼터로 감싼 경우는 단일 문자열로 판단해 오류 없음

`ambiguous redirect` 오류는 프로세스 전체를 종료하지 않고 해당 명령어 파트만 건너뛰므로,  
트리 노드에 `ambiguous` 플래그를 부여해 실행부에 알려주는 방식으로 처리했습니다.

## 파이프와 fd

파이프는 `pipe()` 시스템 콜로 생성하며, fd가 2개 할당됩니다.  
**더 작은 fd가 읽기 끝(read_end), 더 큰 fd가 쓰기 끝(write_end)** 입니다.

```
프로세스 A (ls)         파이프           프로세스 B (grep)
stdout(fd=1) ──────→ write_end(fd=4) ──→ read_end(fd=3) ──→ stdin(fd=0)
```

**연결 과정**

```c
pipe(pipefd);          // pipefd[0]=읽기, pipefd[1]=쓰기
dup2(pipefd[1], 1);    // A의 stdout → 파이프 쓰기 끝
dup2(pipefd[0], 0);    // B의 stdin  → 파이프 읽기 끝
```

**세미콜론 vs 파이프**

| | 세미콜론 | 파이프 |
|---|---|---|
| 데이터 전달 | 없음 | stdout → stdin |
| 실행 방식 | 순차 실행 | 병렬 실행 |
| 사용 목적 | 명령 순서 보장 | 명령 체이닝 |

파이프는 앞 명령어의 출력을 기다리는 명령어와 조합해 사용합니다.  
파이프 앞에 명령어가 없으면 syntax error, 뒤에 없으면 표준 입력 대기 상태가 됩니다.

## 구현 기록

**버스 에러 — 동적 할당 없이 문자열 수정**  
메타 토큰을 공백으로 바꾸려고 직접 초기화했다가 버스 에러가 발생했습니다.  
문자열 리터럴을 수정하려 했기 때문이었습니다. `malloc`으로 동적 할당한 뒤 수정하니 해결됐습니다.

**exit_code를 파싱부에서 `exit()`으로 처리하면 안 되는 이유**  
파싱은 부모 프로세스에서 수행되므로, 파싱 도중 `exit()`을 호출하면 프로그램 전체가 종료됩니다.  
오류 발생 시 트리 노드에 `exit_code`를 부여하고 실행부에서 처리하도록 설계했습니다.  
파싱 단계에서 부여할 `exit_code`는 syntax error의 `258`뿐입니다.

**리디렉션 명령어 토큰 구분 문제**  
리디렉션 기호가 아닌 토큰을 무조건 명령어로 처리하면, 리디렉션 뒤의 파일명 토큰도 포함됩니다.  
컨트롤 토큰(리디렉션)이 파이프가 아닌 상태에서 바로 다음 토큰이 있으면 카운트를 -1하고,  
해당 토큰의 이전 노드가 리디렉션이면 건너뛰는 방식으로 처리했습니다.

**탭 구분자 추가**  
공백만 구분자로 처리했는데 탭도 구분자로 처리해야 했습니다.  
공백 여부를 확인하는 조건문을 함수로 분리하고 탭 조건을 추가해 간단히 해결했습니다.

## 깨달은 점

**파싱이 실행의 절반이다**  
실행 파트보다 파싱이 더 오래 걸렸습니다. 입력을 올바르게 구조화하지 않으면 실행부를 아무리 잘 짜도 동작하지 않습니다. 파서의 견고함이 프로그램 전체의 안정성을 결정합니다.

**트리 구조의 강점**  
계층 구조가 있는 명령어를 선형 리스트로 표현하면 관계를 파악하기 어렵습니다. 트리로 구조화하면 파이프와 리디렉션의 중첩 관계를 직관적으로 표현할 수 있고, 순회 방식으로 실행 흐름도 자연스럽게 구성됩니다.

**메모리 절약을 의식한 설계**  
토큰 문자열을 노드마다 복사하지 않고 인덱스 참조 방식을 쓴 것처럼, 설계 단계에서 메모리 사용을 의식하면 복잡한 자료구조에서도 불필요한 복사를 줄일 수 있습니다.

**exit_code 처리 위치를 설계 단계에서 결정해야 한다**  
어느 단계에서 `exit()`를 호출하냐에 따라 프로그램 전체 동작이 달라집니다. 파싱/실행 파트 분리 시 오류 처리 흐름을 명확히 설계하지 않으면 의도치 않게 프로그램이 종료됩니다.
