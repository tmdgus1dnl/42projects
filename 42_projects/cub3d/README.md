## 과제 개요

`.cub` 파일을 입력받아 3D 1인칭 시점 미로를 렌더링합니다.  
실제 3D 공간을 다루는 것이 아니라, **2D 맵을 레이캐스팅으로 3D처럼 보이게 투영**하는 방식입니다.

```
.cub 파일 파싱
    │
    ├── 텍스처 로드 (N/S/E/W XPM)
    ├── 바닥/천장 색상 설정

    │
    ▼
매 프레임마다
    │
    ├── 화면 열(column)마다 광선 1개 발사 (raycasting.c)
    │       └── DDA 알고리즘으로 벽까지 거리 계산
    │
    ├── 거리에 따라 벽 높이 결정 (render.c)
    │       └── 텍스처 픽셀 샘플링 (texture.c)
    │
    ├── 바닥/천장 색상 채우기
    │
    └── 이미지 버퍼 → MiniLibX 창에 출력 (img_buffer.c)
```

## 레이캐스팅 (DDA)

레이캐스팅은 화면의 각 열(column)마다 하나의 광선을 발사해 가장 가까운 벽까지의 거리를 계산하는 방식입니다.  
거리가 가까울수록 벽을 높게, 멀수록 낮게 그려 원근감을 표현합니다.

**DDA(Digital Differential Analysis) 알고리즘**  
격자 기반 맵에서 광선이 지나가는 셀을 효율적으로 탐색하는 방법입니다.  
x방향 또는 y방향 격자선에 닿을 때까지의 거리를 비교해 더 가까운 쪽으로 한 칸씩 전진합니다.

```
1. 플레이어 위치와 방향 벡터에서 광선 방향 계산
2. 각 축 방향으로 다음 격자선까지의 거리 계산 (delta_dist)
3. x/y 중 더 짧은 쪽으로 전진 (step)
4. 벽(맵에서 '1')에 닿을 때까지 반복
5. 벽까지의 수직 거리 계산 (fisheye 보정 포함)
6. 벽 높이 = 화면 높이 / 수직 거리
```

**Fisheye 보정**  
광선의 실제 유클리드 거리를 그대로 사용하면 화면 양끝이 볼록하게 왜곡됩니다.  
플레이어 시선 방향에 대한 수직 거리를 사용해 어안 효과를 제거합니다.

---

## 텍스처 매핑

벽의 어느 방향(N/S/E/W)에 광선이 닿았는지에 따라 다른 텍스처를 적용합니다.

```
1. 광선이 x벽에 닿았는지 y벽에 닿았는지 판단
2. 벽의 어느 면인지 판단 (N/S/E/W)
3. 벽의 정확한 히트 위치 계산 → 텍스처 x좌표 결정
4. 벽 열 높이에 따라 텍스처 y좌표 비율 계산
5. 해당 텍스처 픽셀을 화면 열에 그리기
```

텍스처는 XPM 파일로 로드하며, MiniLibX의 `mlx_xpm_file_to_image()`로 이미지 데이터를 가져옵니다.

## 설정 파일 파싱

`.cub` 파일은 두 부분으로 구성됩니다.

```
NO ./textures/north.xpm     ← 북쪽 벽 텍스처 경로
SO ./textures/south.xpm
WE ./textures/west.xpm
EA ./textures/east.xpm

F 220,100,0                 ← 바닥 RGB 색상
C 225,30,0                  ← 천장 RGB 색상

111111                      ← 맵 그리드
100101
100000
111111
```

파싱 순서와 규칙:
- 텍스처 경로 4개, 색상 2개가 모두 있어야 합니다
- RGB 값은 0~255 범위여야 합니다
- 맵 그리드는 설정 항목 이후 마지막에 위치해야 합니다
- 맵 이전에 빈 줄이 있으면 오류 처리합니다

## 맵 유효성 검증

맵이 올바르게 구성됐는지 `check_map.c`에서 검증합니다.

**플러드 필(Flood Fill) 방식**  
플레이어 스폰 위치에서 출발해 이동 가능한 모든 빈 공간(`0`)을 탐색합니다.  
탐색 중 맵 경계를 벗어나면 맵이 열려있다고 판단해 오류를 반환합니다.

검증 항목:
- 맵이 벽(`1`)으로 완전히 닫혀있는가
- 플레이어 스폰 위치(`N/S/E/W`)가 정확히 1개인가
- 허용 문자(`0`, `1`, `N`, `S`, `E`, `W`, 공백) 외 문자가 없는가
- 맵이 직사각형이 아닌 경우 짧은 줄의 빈 부분을 공백으로 처리

## 플레이어 이동

플레이어 이동은 방향 벡터와 카메라 평면 벡터로 관리합니다.

```c
// 방향 벡터 (플레이어가 바라보는 방향)
double dir_x, dir_y;

// 카메라 평면 벡터 (화면 너비에 대응하는 가로 방향)
double plane_x, plane_y;
```

**이동**: `dir_x`, `dir_y` 방향으로 좌표 이동. 이동 후 벽(`1`) 충돌 검사.  
**회전**: 회전 행렬로 `dir` 벡터와 `plane` 벡터를 함께 회전.

```c
// Z축 기준 회전 행렬
new_dir_x = dir_x * cos(rot) - dir_y * sin(rot);
new_dir_y = dir_x * sin(rot) + dir_y * cos(rot);
```

## 깨달은 점

**레이캐스팅은 실제 3D가 아니다**  
3D처럼 보이지만 실제로는 2D 맵 위에서 거리를 계산해 화면을 그립니다.  
이 단순한 아이디어로 Wolfenstein 3D 같은 게임이 만들어진 것이 인상적이었습니다.

**파싱이 렌더링만큼 중요하다**  
`.cub` 파일 파싱과 맵 유효성 검증에 예상보다 많은 시간이 걸렸습니다.  
어떤 입력이 들어와도 명확하게 오류를 잡아내는 파서를 만드는 일이 쉽지 않았습니다.

**벡터 회전의 일관성**  
플레이어 회전 시 방향 벡터(`dir`)와 카메라 평면 벡터(`plane`)를 항상 함께 회전해야 합니다.  
하나만 회전하면 화면이 올바르게 렌더링되지 않습니다.

**팀 작업에서 모듈 분리가 핵심이다**  
파싱/렌더링/이동 파트를 명확히 분리해두니 팀원과 충돌 없이 동시에 작업할 수 있었습니다.  
인터페이스를 먼저 정의하고 구현을 나누는 방식이 효율적이었습니다.
