# philosophers

> 42Seoul | C · POSIX Thread/Process | 점수: 125/125 | 소요 기간: 3주 | 재시도: 4회

식사하는 철학자 문제(Dining Philosophers Problem)를 구현한 병렬 프로그래밍 프로젝트입니다.  
**Mandatory** 파트는 스레드·뮤텍스, **Bonus** 파트는 프로세스·세마포어로 각각 구현해 두 가지 병렬 모델을 모두 경험했습니다.

## 과제 개요

원탁에 N명의 철학자가 앉아 있고, 철학자 사이마다 포크가 하나씩 놓여 있습니다.  
철학자는 **생각 → 포크 2개 집기 → 식사 → 수면** 사이클을 무한 반복하며,  
한 명이라도 굶어 죽으면 시뮬레이션이 종료됩니다.  
철학자들은 서로 대화하지 않으며, 누가 죽을 위기에 처했는지 알 수 없습니다.

```
./philo number_of_philosophers time_to_die time_to_eat time_to_sleep [must_eat_count]
```

| 인자 | 설명 |
|---|---|
| `number_of_philosophers` | 철학자 수 (= 포크 수) |
| `time_to_die` (ms) | 마지막 식사 후 이 시간이 지나면 사망 |
| `time_to_eat` (ms) | 식사 소요 시간 (포크 2개 점유) |
| `time_to_sleep` (ms) | 수면 소요 시간 |
| `must_eat_count` (선택) | 모든 철학자가 이 횟수만큼 먹으면 종료 |

## 프로그램 구조

### Mandatory (스레드)

```
main
├── 뮤텍스 배열 초기화 (포크 수만큼)
├── 철학자 스레드 N개 생성
│   └── [각 스레드] 생각 → 포크 집기 → 식사 → 포크 내려놓기 → 수면 → 반복
└── 메인 스레드: 철학자 사망 감시, 시뮬레이션 종료 처리
```

### Bonus (프로세스)

```
main (모니터링 프로세스)
├── 세마포어 초기화
├── 철학자 프로세스 N개 fork
│   └── [각 프로세스] 포크 집는 스레드 생성 + 시간 계산 루프
│       └── [포크 집는 스레드] sem_wait으로 포크 획득 대기
└── 메인: sem_wait(dead) 대기 → 사망 감지 시 전체 kill(SIGTERM)
    모니터링 스레드: sem_wait으로 식사 횟수 카운트
```

## Mandatory: 스레드 기반 구현

### 교착 상태(Deadlock) 방지 — 시작 시간차 부여

모든 철학자가 동시에 왼쪽 포크를 집으려 하면 교착 상태가 발생합니다.  
**짝수 번째 철학자는 즉시 식사 시작, 홀수 번째 철학자는 `time_to_eat / 2`만큼 대기** 후 시작하도록 했습니다.  
포크를 집는 순서의 대칭이 깨져 교착 상태가 구조적으로 발생하지 않습니다.

### 포크별 개별 뮤텍스 분할

처음엔 전역 뮤텍스 하나로 모든 포크를 보호했습니다.  
이 경우 어떤 철학자가 포크를 집는 동안 다른 모든 철학자가 대기해야 하는 문제가 있었습니다.  
포크마다 개별 뮤텍스를 생성해 필요한 포크만 잠그도록 변경하니 락 경합이 크게 줄었습니다.

```c
pthread_mutex_t *forks; // 포크 수만큼 동적 할당
// i번 철학자는 forks[i]와 forks[(i-1+n)%n]만 잠금
```

또한 `mutex_lock ~ mutex_unlock` 사이에 코드를 1~2줄만 유지하도록 함수로 분리해 락 보유 시간을 최소화했습니다.  
동기화가 적을수록 문맥 전환도 적고, 그로 인한 오버헤드도 줄어 성능과 정확성 모두 향상됐습니다.

### 시간 측정 — usleep 쪼개기

`usleep`으로 긴 시간을 한 번에 재울 경우, 그 사이에 철학자가 죽어야 하는 타이밍을 놓칠 수 있습니다.  
`usleep(200)` 단위로 반복하며 `gettimeofday`로 경과 시간을 실시간으로 측정하는 방식을 선택했습니다.  
생각하는 행동은 시간 제한이 없어 미리 계산이 불가능하기 때문에 이 방식이 유일한 선택이었습니다.

### 동시 시작 보장

스레드 생성 시점 차이로 타임스탬프 기준 죽어야 할 타이밍에 죽지 않는 문제가 발생했습니다.  
모든 스레드의 **시작 시각을 현재 시간 + 100ms로 고정**하고,  
전체 스레드가 생성된 후 그 시각에 일제히 시뮬레이션을 시작하도록 해 해결했습니다.

## Bonus: 프로세스 기반 구현

### 프로세스 간 통신 제약

프로세스는 독립된 주소 공간을 가지므로 스레드처럼 변수를 직접 공유할 수 없습니다.  
허용 함수 내에서 프로세스 간 데이터를 공유하는 수단은 사실상 **이름 있는 세마포어**뿐이었습니다.

이름 있는 세마포어(`sem_open`)는 파일 시스템(`/dev/shm`)에 생성되어 시스템 전역에서 접근 가능합니다.  
이 특성을 활용해 포크, 식사 횟수(`ate_cnt`), 사망 신호(`dead`)를 세마포어로 관리했습니다.

### 포크 집는 스레드 분리

`sem_wait`으로 포크를 기다리면 해당 코드에서 실행이 완전히 멈춥니다.  
이 상태에서는 시간 계산도 사망 처리도 불가능합니다.  
결국 **각 철학자 프로세스 안에 포크 집는 스레드를 하나씩 생성**하는 구조를 선택했습니다.

```
철학자 프로세스
├── 메인 루프: 경과 시간 계산, time_left 관리, 사망 감지
└── 포크 집는 스레드: sem_wait(fork)로 포크 획득 대기
```

프로세스가 `SIGTERM`을 받으면 종속된 스레드도 자동 정리됩니다.  
단, 포크를 집은 후 정상 종료가 필요한 스레드는 `pthread_join`으로 처리했습니다.

### 오염된 세마포어 문제

프로그램을 `Ctrl+C`로 강제 종료하면 `sem_unlink`가 호출되지 않아 세마포어가 파일 시스템에 잔류합니다.  
다음 실행 시 오염된 세마포어로 시뮬레이션이 비정상 동작하는 문제가 반복됐습니다.  
세마포어 생성 전에 항상 먼저 `sem_unlink`를 호출해 잔류 세마포어를 제거하는 방식으로 해결했습니다.

### 동시 시작 보장 (프로세스)

스레드와 달리 프로세스는 100ms 안에 전부 생성된다는 보장이 없습니다.  
각 자식 프로세스가 생성 완료 후 `sem_post(ready)`를 호출하고,  
메인 프로세스는 `ready` 세마포어 카운터가 철학자 수에 도달하면 `sem_post(start)`를 통해 전체를 동시에 출발시켰습니다.

## Data Race 발생과 해결

`-fsanitize=thread` 옵션을 처음 적용했을 때 예상보다 훨씬 많은 레이스가 탐지됐습니다.  
결과값이 정상으로 보여도 레이스가 발생하고 있다는 사실이 의외였습니다.

**① 공유 변수 최소화**  
여러 곳에서 쓰이는 데이터를 직접 공유하지 않고, 그 정보를 담은 플래그 변수를 별도로 선언해 플래그만 동기화 처리했습니다.  
쓰이는 곳마다 동기화 처리를 하면 성능이 크게 저하되므로, 공유가 필요한 순간에만 동기화되도록 범위를 좁혔습니다.

**② 락 범위 최소화**  
`mutex_lock ~ mutex_unlock` 사이에 코드를 1~2줄만 유지하고 함수로 분리했습니다.  
락 보유 시간이 짧을수록 문맥 전환이 줄어 성능과 정확성이 모두 향상됐습니다.

| | 변경 전 | 변경 후 |

## 트러블슈팅

**인덱스 변수 Data Race**  
스레드 생성 시 인덱스를 포인터로 넘겼더니 모든 스레드가 같은 변수를 참조해 레이스가 발생했습니다.  
각 스레드마다 독립된 노드 구조체를 동적 할당해 인덱스를 개별 멤버 변수로 관리하는 방식으로 해결했습니다.

**Bonus 세마포어 오염**  
`Ctrl+C` 강제 종료 후 재실행 시 시뮬레이션이 비정상 동작했습니다.  
세마포어 생성 전 `sem_unlink` 선행 호출로 해결했습니다.

**타임스탬프 불일치**  
스레드/프로세스 생성 시점 차이로 죽어야 할 타이밍에 죽지 않는 문제가 발생했습니다.  
전체 생성 완료 후 고정된 시작 시각에 일제히 출발하는 방식으로 해결했습니다.

**sem_wait 중 사망 감지 불가**  
`sem_wait` 상태에서는 시간 계산이 불가능해 사망을 감지할 수 없었습니다.  
포크 획득 대기를 별도 스레드로 분리하고, 프로세스 메인 루프에서 시간 계산과 사망 감지를 담당하도록 역할을 나눴습니다.

## 깨달은 점

**병렬 프로그래밍에서 실행 순서는 예측 불가능하다**  
스레드/프로세스의 실행 순서는 OS 스케줄러가 결정합니다. 순서를 가정하고 코드를 짜면 반드시 문제가 발생합니다. 동기화 기법으로 명시적으로 관리해야 합니다.

**결과가 맞아도 레이스는 있을 수 있다**  
`-fsanitize=thread` 없이는 Data Race를 발견하기 어렵습니다. 정상 동작처럼 보여도 내부적으로 레이스가 발생하고 있을 수 있습니다.

**락은 짧게, 분할해서**  
전역 락은 편하지만 성능을 크게 떨어뜨립니다. 자원별로 락을 분할하고 락 보유 시간을 최소화하는 것이 병렬 프로그래밍의 핵심입니다.

**이름 있는 세마포어는 시스템 전역에 잔류한다**  
`/dev/shm`에 파일로 생성되므로 프로그램 종료 후에도 남아 있습니다. 프로그램 시작 시 반드시 `sem_unlink`로 정리해야 합니다.
